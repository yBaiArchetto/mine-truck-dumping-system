# 进度计划

> 项目：矿井货车倒矿智能管控系统开发项目
> 招标人（甲方）：华盛矿业（集团）有限公司 · 招标编号：HXKY-ZB-2026-0325
> 本目录用途：存放**实施计划与进度排布**两类文件，回答"怎么干、谁干、干多久、风险在哪、如何验收"

本目录是仓库文档链的第 ② 环：上游是需求依据（招标书 / 投标书 / 合同），下游是线框与原型。它把「甲方要什么」翻译成「团队按什么节奏交付什么」。

## 四、WBS 概要

任务分解取自 `项目1.mpp`：5 个阶段、21 个工作包、3 个里程碑。

| 阶段                        | 起止日期                | 工期                  | 主要工作包                                                   | 里程碑                                  |
| --------------------------- | ----------------------- | --------------------- | ------------------------------------------------------------ | --------------------------------------- |
| 第一阶段 项目启动与需求确认 | 2026-10-19 ~ 2026-11-27 | 6 周                  | 现场调研、需求规格、评审与基线、概设详设、数据库与接口设计   | **M1 需求基线 V1.0 确认（2026-11-13）** |
| 第二阶段 系统开发           | 2026-11-30 ~ 2027-02-05 | 10 周                 | 识别与档案、计次统计、围栏轨迹、看板、预警工单、接口适配、H5、系统管理 | —                                       |

| 第四阶段 培训与试运行       | 2027-03-01 ~ 2027-04-30 | 9 周（试运行 2 个月） | 3 场次 12 课时培训、连续试运行、缺陷修复与调优               | —                                       |

**关键路径**：1.1 → 1.2 → 1.3 → 1.5 → 2.1 → 2.2 → 2.4 → 3.1 → 3.2 → 3.3 → 4.2 → 5.1。该路径上任一任务延期一天，总交付即延后一天，周报单独跟踪。

## 五、`项目1.mpp` 使用说明

### 5.1 打开方式

| 环境                   | 方式                                                         |
| ---------------------- | ------------------------------------------------------------ |
| 已装 Microsoft Project | 直接双击打开；建议切到「甘特图 + 任务名称/工期/开始/完成/前置任务」视图 |
| 无 Project             | 用 Project 网页版、Project Viewer 打开，或直接阅读实施计划文档第 5 章（WBS 已完整转录） |
| 仅需查看时间线         | 在 Project 中导出 PDF 或截图，随报告附在附录                 |

> 该文件最后保存时间为 2026-10-19 16:18，与实施计划文档 V0.2.1 的编制日期一致。

### 5.2 文件内的组织方式

- 顶层为项目名与摘要任务「矿井货车倒矿智能管控系统开发项目」；
- 一级任务为 5 个阶段（1. 项目启动与需求确认 / 2. 系统开发 / 3. 测试与部署 / 4. 培训与试运行 / 5. 验收与收尾）；
- 二级任务为 21 个工作包，编号与实施计划文档表 13 一一对应；
- 3 个里程碑任务单独列为里程碑行。

### 5.3 编辑规则

1. **只改 mpp，不改 docx 的数字**：工期或日期调整先在 mpp 中重排，再同步到 docx，避免两处不一致；
2. **保持任务编号不变**：`2.3` 始终指「电子围栏与轨迹管控模块」，便于周报、缺陷单、文档交叉引用；
3. **不删除阶段层级**：即使某阶段内容缩减，也保留行并标注「并入某阶段」，保持历史可比；
4. **改完立即升版本**：每次修改同步更新 docx 版本号与修订记录（如 V0.2.1 → V0.2.2），并在根目录 README 变更记录登记；
5. **二进制文件不要手工合并**：mpp 为二进制格式，冲突无法文本合并，多人协作时约定"同一时间仅一人修改"。

## 六、工期基准与已知偏差

本计划总工期为 **2026-10-19 至 2027-05-14，约 6.9 个月**，而合同约定的建设周期为 **约 6 个月**，验收节点相差约 3 周。偏差来源：

| 来源         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| 试运行要求   | 合同要求连续试运行不少于 2 个月，不可压缩                    |
| 测试窗口偏紧 | 第三阶段仅 3 周，需同时完成集成、性能、部署与联调，缺少吸收缺陷的余量 |
| 评审等待     | 第一阶段设计评审需甲方参与，等待时间不可控                   |

实施计划文档 5.6 节给出三种处理方式：**A** 顺延验收节点并签补充协议（推荐）、**B** 培训前移与部署并行回收约 1 周、**C** 压缩试运行至 6 周（存在验收争议风险）。该事项列入 M1 评审待确认清单，未确认前不得对外承诺验收日期。

## 七、计划变更流程

```
变更申请（书面）
   ↓
影响分析（工期 / 工作量 / 成本 / 风险）
   ↓
双方确认（补充协议或变更单）
   ↓
修改 项目1.mpp → 同步 docx → 升版本号
   ↓
更新根目录 README 的变更记录 + 通知项目组
```

未经书面确认的口头调整，一律不进入基线；执行中出现的偏差记录在项目周报的问题台账中，每周销项。
